# SKILL: Вынос общей логики в `common`

## 0. Когда применять, а когда — нет

**Применять**, если:
- Один и тот же класс/правило присутствует в 2+ сервисах.
- Разные сервисы возвращают **разные** ответы на одно и то же нарушение (например, `task-service` отдаёт `403`, а `project-service` — `404`).
- DTO задачи/проекта дублируются и уже начали расходиться по полям.
- HTTP-клиент для межсервисных вызовов скопирован в нескольких местах.

**НЕ применять**, если:
- Логика встречается только в одном сервисе — вынос в `common` без причины увеличит связанность.
- Речь о добавлении нового эндпоинта — используй `implement-api-endpoint`.
- Речь о правке одного бизнес-правила — сначала проверь, действительно ли оно общее, или так только кажется.

## 1. Preflight

1. Прочитай `pom.xml` в корне — как объявлены модули и как `common` подключён к сервисам.
2. Прочитай `common/` — что там уже лежит. **Категорически нельзя дублировать то, что уже есть в `common`.**
3. Прочитай `SERVICES.md` — там описаны потоки между сервисами; пойми, какие сущности пересекаются.
4. Прочитай `openapi.yaml` — если дублируется DTO, контракт в OpenAPI уже должен совпадать, иначе сначала приведи OpenAPI к единому виду.
5. Grep по каждому сервису, чтобы подтвердить дублирование: `grep -rn "<имя класса>" user-service project-service task-service`.

## 2. Что уже живёт в `common` (типовые кандидаты)

В проекте такого класса обычно в `common` лежат:
- общие DTO (например, `ApiError`, `PageResponse`, `UserRef`);
- базовые исключения (`NotFoundException`, `ForbiddenException`, `ValidationException`);
- HTTP-клиент для вызовов между сервисами;
- константы заголовков (в том числе `X-User-Id`);
- утилиты, не зависящие от домена.

**Правило:** если артефакт упоминает `Task`, `Project` или `Membership` — он **не идёт** в `common`. `common` не знает про доменные сущности сервисов.

## 3. Граница `common` (это главное правило)

| Идёт в `common` | НЕ идёт в `common` |
|---|---|
| `ApiError`, `PageResponse` | `TaskDto`, `ProjectDto` |
| `ForbiddenException`, `NotFoundException` | `TaskStatus` enum |
| Константы заголовков | Проверка прав `ProjectMembership` |
| HTTP-клиент к другим сервисам | Доменные инварианты задач |
| Утилиты для дат/строк | Репозитории и JPA-сущности |

Проверка прав **остаётся** в `project-service` как владельце модели прав. Если `task-service` должен спрашивать «можно ли?» — он делает HTTP-вызов в `project-service`, а не тащит модель к себе в `common`.

## 4. Пошаговый алгоритм

1. **Зафиксируй baseline.** Прогони `mvn -pl <service> -am test` для каждого затронутого сервиса **до** изменений. Если что-то красное — сначала разберись, иначе не отличишь свои поломки от существующих.
2. **Опиши расхождение.** Сравни реализации дублей и явно перечисли различия (поля, коды ответов, тексты ошибок). Это — спецификация будущего общего класса.
3. **Реши, какая версия правильная.** Не «средняя», а та, что соответствует `openapi.yaml` и бизнес-правилам из README. Если версии конфликтуют с OpenAPI — сначала правь OpenAPI, потом код.
4. **Создай артефакт в `common`.**
   - Пакет: следуй существующей структуре (`common/src/main/java/.../`).
   - Имя: как в проекте (например, `ApiError` — не `ErrorResponse`, если в проекте первое).
5. **Подключи `common` к сервисам.** Обычно зависимость уже объявлена в их `pom.xml` — проверь, не добавляй заново.
6. **Удали дубли из сервисов** и переключи импорты. Не оставляй «старые» копии даже как deprecated — в Java это приводит к тому, что часть кода продолжает пользоваться старым классом.
7. **Проверь сериализацию.** Если DTO дублировался и отличался полями — после унификации JSON-ответы сервисов изменятся. Это должно быть отражено в `openapi.yaml` и в curl-примерах README.
8. **Прогони тесты каждого сервиса отдельно:** `mvn -pl <service> -am test`. Не «сборку всего проекта» — именно по сервисам, чтобы сразу видеть, где сломалось.
9. **Подними всё через Docker:** `docker compose up --build` и прогони полный smoke-сценарий из README (регистрация → проект → задача → статус → удаление).

## 5. Definition of Done

- [ ] Артефакт лежит в `common` и не упоминает доменные сущности сервисов
- [ ] Во всех затронутых сервисах дубли удалены (grep не находит старых копий)
- [ ] Поведение сервисов после унификации совпадает (одинаковые коды ответов и структура JSON)
- [ ] `openapi.yaml` отражает актуальные контракты
- [ ] `mvn -pl <service> -am test` зелёный для каждого сервиса
- [ ] `docker compose up --build` поднимает все три сервиса
- [ ] Smoke-сценарий из README проходит
- [ ] В `common` не появилось доменных зависимостей на `Task`, `Project`, `Membership`

## 6. Частые ошибки

- Вынести в `common` `ProjectMembership` или проверку прав — это домен `project-service`, не общее.
- Оставить в сервисах «старые» классы рядом с новыми — агенты и люди будут пользоваться разными версиями.
- Унифицировать DTO «по среднему», не сверившись с `openapi.yaml` — сломает контракт.
- Прогнать `mvn test` по всему проекту и радоваться одному зелёному билду — при таком рефакторинге важно видеть, какой именно сервис сломался.
- Добавить в `common` зависимость на Spring Web только потому, что одному сервису так удобнее — `common` должен оставаться лёгким.
- Поменять имя класса в `common`, не поправив все импорты (в Java это ошибка компиляции, но её легко «залечить» добавлением дубля — не делай так).
