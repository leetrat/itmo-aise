## Шаг 0: Выбор кодовой базы

В качестве кодовой базы был выбран собственный репозиторий с курса Объектно-ориентированного программирования - платформа для управления задачами и проектами.

Чек-лист самопроверки:
Есть выраженное разделение слоёв (controllers/handlers ≠ business logic ≠ data access) -- не один файл на 200 строк - да, в каждом сервисе:
- Controller → AuthController, ProjectController, TaskController и т.д.
- Service → бизнес-логика + DTO-маппинг
- Repository → Spring Data JPA
- Model → JPA-сущности
Разумный размер: 1000–10000 строк -- не тривиальный и не безразмерный 
- ~5,500 строк Java-кода (source + tests). Вместе с конфигами и документацией ~7,400.
- Есть тесты, которые реально гоняются (npm test pass/fail) -  да
- Есть хотя бы 5-7 неочевидных, но обнаружимых конвенций (свой error-handling паттерн, naming convention, helper-обёртки и т.п.):
  1. Dual Implementation Pattern -- каждый сервис имеет Jpa*Service (@Primary) + Mock*Service (in-memory ConcurrentHashMap)
  2. Error handling -- бизнес-ошибки бросаются как IllegalArgumentException с кодом, GlobalExceptionHandler маппит на HTTP-статусы через ErrorResponse
  3. DTOs as Records -- все DTO -- Java 17 records, вложены в контейнерные классы (TaskDto.CreateRequest)
  4. DevModeAuthFilter -- JWT bypass через X-User-Id header для dev-окружения
  5. API versioning -- все эндпоинты под /api/v1/
  6. REST status codes -- 201 для создания, 204 для удаления, 409 для конфликтов, 422 для бизнес-нарушений
  7. Permission-Based Authorization -- все операции проверяют права через projectServiceClient.hasPermission()
  8. ErrorCode enum -- 20 кодов ошибок в common, единый язык между сервисами

- Популярный стек, с которым агент нормально работает - Java 17 + Spring Boot 3.2 + Spring Cloud + JPA/Hibernate + Maven

## Шаг 1: Baseline -- без правил

Агенту была дан промпт: “Сделай фичу Экспорт данных пользователя: эндпоинт/кнопка собирает данные пользователя из нескольких таблиц/сервисов в один файл (JSON/CSV), с проверкой прав доступа (только свои данные).” Было сделано 3 прогона, их результаты зафиксированы в ветках baseline-attempt-x

Каждый запуск занял разное количество времени (от 20 минут до 50).

> **baseline-attempt-1** -- подход «рабочий конвейер»: сделано сквозно, от агрегирующего `ExportController` (`GET /api/v1/users/me/export?format=json|csv`) в user-service до новых эндпоинтов task-service с проверкой `userId == X-User-Id` (403). Данные профиля + проекты + задачи + комментарии + вложения собираются через два HTTP-клиента, сериализуются в JSON/CSV с ручным escaping и `Content-Disposition`. Минусы: «только свои данные» соблюдается частично -- экспортируются *все* задачи/вложения в проектах, где состоит пользователь (включая чужие); клиенты молча глотают ошибки; CSV собран вручную без библиотеки; DTO продублированы между сервисами; нет docker-проброса URL (локальные `localhost`), нет тестов и UI-кнопки.

> **baseline-attempt-2** строит полную цепочку в трёх сервисах: user-service `GET /api/v1/users/me/export` агрегирует профиль + проекты (`/api/v1/export/memberships`) + задачи/комменты/вложения (`/api/v1/export/data`), с JPA и Mock реализациями, UI-кнопкой, docker-compose пробросом URL и `GlobalExceptionHandler` (404 для `USER_NOT_FOUND`, 503 при недоступности сервисов). Скоуп жёстко «свой»: `findByCreatorId`/`findByAuthorId`/свои вложения, с ролями и правами в проектах -- как задумал attempt-3, но доведено до конца.

> **baseline-attempt-3** -- подход «концепт/скаффолдинг»: заявлено больше, но фактически не собирается и не работает. Ветка не компилируется: сервисы ссылаются на `ExportDto.*` (project/task), которого нигде нет, а `SecurityConfig` user-service инжектит несуществующий `DevModeAuthFilter`. HTTP-эндпоинтов экспорта нет вообще -- кнопка в `TaskManagerClient` зовёт `/api/v1/users/me/export`, которого нет (404). Зато есть OpenAPI-схема, докер-проброс URL, юнит-тест и семантически более верный отбор: строго «своё» (`findByCreatorId`, `findByAuthorId`) с ролями и правами в проектах.

**Разница по сути**:  attempt-2 -- единственный, кто добавил `DevModeAuthFilter` + правку `SecurityConfig` в user-service. На main там вообще нет фильтра, так что `anyRequest().authenticated()` режет любой эндпоинт (403) -- значит, эндпоинт attempt-1 в runtime физически недоступен (403), а у attempt-3 эта же попытка сломана (класс не создан → не компилится).

## Шаг 2: AGENTS.md и reusable skill

`AGENTS.md` был создан при помощи команды `/init` в OpenCode. Эта стандартная команда поддерживается во многих агентах и используется для общего описания кодовой базы и ограничений.
Скилл `extract-shared-logic-to-common` представляет собой набор инструкций для агента, которому необходимо сократить и вынести общую логику в модуль `Common`.

## Шаг 4: Проверка генерализуемости

Для генерализуемости была выбрана на проверку следующая фича:
> Смена пароля/email в личном кабинете — форма с валидацией (текущий пароль верен, новый email не занят), хешированием, инвалидацией старых сессий, возможно — письмом-подтверждением.

**Реализация фичи.** Полный стек: `POST /api/v1/users/me/password` и `POST /api/v1/users/me/email` (JPA + Mock, дуальная реализация), `ChangePasswordRequest`/`ChangeEmailRequest` с `@Valid` (@NotBlank, `@Size(min=8,max=128)`, `@Email`); сервер проверяет текущий пароль через `passwordEncoder.matches`, новый пароль хешируется (`passwordEncoder.encode`), email проверяется на занятость (`existsByEmail` → `DUPLICATE_EMAIL`), при совпадении с текущим — no-op. В UI добавлен «Личный кабинет» с формами и клиентской валидацией (заполненность, min 8, совпадение введённых паролей). Письма-подтверждения нет — опциональный пункт пропущен.

**Инвалидация сессий — частичная.** Реализовано честно для refresh-сессий: добавлено поле `credentials_version` у User, JWT несёт claim `ver`, при смене пароля/email версия инкрементится + `refreshTokenRepository.deleteByUserId()`; в `refreshToken`-флоу проверяется сохранённый токен и совпадение версии. НО access-токены не проверяются по версии нигде (DevModeAuthFilter просто доверяет `X-User-Id`, JWT-фильтра для access нет) — старые access-сессии живут до истечения, а в dev-режиме «сессии» фактически привязаны к заголовку, а не к токену. То есть инвалидация работает только для refresh-части.

**Инженерия и качество.** Дисциплина конфиг-запуска видна: AGENTS.md + `check.js` (19 правил), 10 новых юнит-тестов в `MockAuthServiceTest` (верный/неверный пароль, занятой/совпадающий email, неизвестный юзер, инвалидация refresh после смены), `target/`-отчёты закоммичены — сборка гонялась. Слабые места: Mock сравнивает пароли в открытом виде (ограничение мока, но «параллельность» с JPA нарушена), смена пароля не заставляет текущего клиента перелогиниться, реальная проверка личности по-прежнему на доверии к `X-User-Id`.

Чтобы перевести результат прогонов в измеряемую метрику, был разработан автономный скрипт `check.js`. Требования к нему были: конвенции не выдумывать — брать только из `AGENTS.md` и скилла `extract-shared-logic-to-common`; проверка должна быть детерминированной (одинаковые цифры на одинаковом коде в любой ветке); считать нарушения по файлам, изменённым агентом, а не по всей кодовой базе; и не гоняться по коду под желаемый результат.

1. Проверка валидации request-рекордов велась «по файлу» (если в файле уже есть одна jakarta-аннотация, новые незаполненные рекорды проходили) → заменена на построчный анализ заголовка каждого рекорда.
2. Один и тот же «несуществующий» код ошибки считался дважды (по `Jpa*Service` и по `Mock*Service`) → теперь считается уникальный код на модуль со списком всех точек выброса.
3. Список внутренних эндпоинтов для проверки `permitAll` был захардкожен по формулировкам `AGENTS` и пропускал `/active-count` → теперь эндпоинты выводятся из call-сайтов клиентов (`RestTemplate` + `@Value("${services.<x>-service.url...}")`).
4. Проверка pom-зависимостей ложно срабатывала на собственный `<artifactId>` сервиса → проверка только на зависимость от модуля `common`.
   Формат вывода — по каждому модулю (`SERVICE: <имя>`), по каждой конвенции счётчик, в конце `TOTAL` на модуль и `PROJECT TOTAL`; для каждого нарушения — файл и строка. Поддерживаются режимы:
5. Только заданные файлы/папки: `--scope <path>[,<path>]`;
6. файлы, изменённые относительно git-ссылки: `--base <ref>`;
7. Машинночитаемый отчёт: `--json report.json`.

Результат прогона по всему репозиторию на каждой ветке:

| Ветка | common | project-service | task-service | user-service | PROJECT TOTAL |
|---|---|---|---|---|---|
| baseline-attempt-1 | 5 | 1 | 4 | 6 | 16 |
| baseline-attempt-2 | 5 | 1 | 3 | 5 | 14 |
| baseline-attempt-3 | 5 | 1 | 3 | 3 | 12 |
| configured-attempt-1 | 5 | 1 | 2 | 2 | 10 |
| configured-attempt-2 | 5 | 1 | 2 | 2 | 10 |

Сама по себе цифра неприятная, во всех ветках одинаково присутствует «дно» из 10 нарушений, не связанных с работой агента — 5 в `common` (4 DTO-класса вместо records + `spring-boot-starter-web` в pom), 1 в `project-service` (`@RequestBody` без `@Valid`), 2 в `task-service` (коды `DUPLICATE_TAG`/`NOT_FOUND` не входят в `ErrorCode`), 2 в `user-service` (`refresh` без `@Valid`, `HashMap` вместо `ConcurrentHashMap` в `MockAuthService`). Значимой является разность относительно этого уровня:

| Отклонение от уровня | baseline-1 | baseline-2 | baseline-3 | configured-1 | configured-2 |
|---|----|---|---|---|---|
| Новые коды ошибок вне `ErrorCode` | +1 | +1 | 0 | 0 | 0 |
| Нет юнит-теста `Mock*Service` (task) | +1 | +1 | +1 | 0 | 0 |
| Новые внутренние эндпоинты не в `permitAll` | +3 | +2 | 0 | 0 | 0 |
| `DevModeAuthFilter` отсутствует/битый | +1 | 0 | +1 | 0 | 0 |
| **Δ к 10** | **+6** | **+4** | **+2** | **0** | **0** |

**Вывод:** Метрика воспроизвела наблюдаемое вручную различие веток: baseline-прогоны накопили от +2 до +6 новых нарушений конвенций (в attempt-1 — «сквозной конвейер» без регистрации новых внутренних эндпоинтов в `SecurityConfig`, без тестов и с кодами ошибок вне enum; attempt-3 дополнительно сломан на уровне компиляции — `SecurityConfig` инжектит несуществующий `DevModeAuthFilter`), тогда как configured-прогоны остались ровно на базовом уровне 10 — новых нарушений агент не внёс. При этом в конфигурированных ветках видна и обратная сторона «послушания»: экспорт реализован способом, который скрипт не проверяет, а ручная ревизия отмечает как слабое место (дуальная реализация экспорт-логики не везде, переиспользование `ExportUtils` в `user-service`).
